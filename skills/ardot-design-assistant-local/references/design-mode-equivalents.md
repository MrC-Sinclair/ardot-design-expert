# 宿主注入块 · 等价行为约定

> **这份文件解决什么问题**：有些宿主会向会话注入指令块，把一部分决策**提前替你做掉了**。
> 在没有这类注入的环境里，这些结论不存在，模型就会退回"每步都问用户"——体验断裂，
> 还容易建错文件、烧错生图额度。
>
> 本文把三个指令块的**默认行为**转写成可判定规则：什么信号 → 什么动作 → 什么情况下才该问用户。
> **注入存在时以注入为准**（它有当前会话的上下文），本文只是它的等价物，不是替代品。

---

## 判定总则（三条）

1. **先看有没有注入**。`SKILL.md`「能力探测清单」会先给出四项结论；其中第 2 项为"有注入"时，
   该维度直接服从注入，本文对应小节**跳过**。三项探测都没做就先读本文 = 空中楼阁。
2. **没注入 ≠ 要问**。默认行为是明确的（下文给出），只有落进「该问」区间才发问。
   每个任务最多问 **1 轮**、每轮 ≤ 3 个问题——问完就执行，不要连环确认。
3. **冲突裁决顺序**（高 → 低）：
   用户显式指令 > 宿主注入块 > 本文默认 > 类型指南 / 风格库检索结果。
   低优先级与高优先级冲突时，**服从高的，并在交付说明里写一句取舍原因**。

## 一、`<ardot_file_directive>` → 文件开关

宿主注入时它直接给出 `create` / `open` / `ambiguous`。等价规则如下。

### 1.1 判定表

| 用户信号 | 动作 | 说明 |
|---|---|---|
| 有设计意图 + 没给目标文件（"画个落地页""做个 dashboard""设计一版海报"） | **create** | 直接建，不问 |
| 给了 `.ardot` 文件链接 / 纯数字 fileId / 明确文件名 | **open** | 直接开，不问 |
| "改一下这个""在这个基础上""接着上一版" + 有上下文文件 | **open** | 沿用当前会话/编辑器已打开的文件 |
| "创建 / 做一个 / 建个 / 帮我搞个" + **非设计产物**（issue、文档、表格、脚本、PPT、邮件） | **ambiguous** | ⛔ 不建画布文件，先确认一句 |
| "创建 / 做一个" + 宾语是抽象名词但不含设计名词（"做个东西""搞个页面那种"） | **ambiguous** | 问一句"是要画布设计稿，还是先出规格/预览" |
| 纯咨询（"Ardot 能做什么""这个规范怎么理解"） | **不建不开** | 只回答，不动画布 |

### 1.2 执行纪律（与注入版一致）

- **幂等**：同一个任务最多一次 `create_design` 或 `open_design`。调用即视为已完成。
- 异步加载：调用后**等就绪**再发其他 MCP 调用，不要和读操作并发。
- 确认文件用 `fetch_file_info`，**不是**再调一次 create/open。
- 新建空文件根 PageID 为 `0:1`，此时跳过 `fetch_editor_state`（无内容可读）。
- `create_design` 支持 `fileName`；不给就用默认名。命名建议用用户 brief 里的主体词，别用 `Untitled`。

### 1.3 失败与降级

| 情况 | 处置 |
|---|---|
| 通道里**没有** `create_design` / `open_design` | 不要假装建成功。引导用户在 Ardot 编辑器里手动建/开，然后从 Step 0 继续 |
| create 调用报错 | **不重试第二次**。先 `fetch_file_info` 看是否其实已建成功；仍无 → 引导手动建 |
| open 的 fileUrl 无效 | 请用户重新给链接，不要猜 fileId |

> ⛔ 禁止：为"确认是否建成功"二次调用 create/open；在 ambiguous 情况下先建后问。

## 二、`<ardot_image_gen>` → 图片模式选择

宿主注入 `mode="ai"`（真图）或 `mode="placeholder"`（占位）。没注入时按下面的决策树自己判。

### 2.1 默认决策树（按顺序，命中即停）

| 顺序 | 条件 | 结论 |
|---|---|---|
| 1 | 用户明说"要真图 / 成品 / 直接投放 / 真实照片" | **ai** |
| 2 | 交付物是**海报 / 封面 / banner / 电商主图**（成品像素导向） | **ai** |
| 3 | 用户明说"先看结构 / 草稿 / 线框 / 别花钱" | **placeholder** |
| 4 | 任务是**结构性**的（后台面板、表单、表格、设置页、设计系统页） | **placeholder** |
| 5 | 图片是**唯一主角**（P02 SubjectHero / L02 Cinematic / 摄影主导的 hero） | **ai** |
| 6 | 其余（默认） | **placeholder** |

判定依据是**交付形态**，不是名词。同一个"海报"词，说"先出个结构给我看"就是 placeholder。

### 2.2 该问用户的边界（只有这两条）

1. 预计图片数 **> 3 张**，或总消耗估算 **> 30 credits** → 先报预算再问（"这套要生成 N 张图，约 X credits，继续吗"）。
2. 交付形态**自相矛盾**（"随便出一版能直接发的，但先别花钱"）→ 问一句以哪个为准。

除此之外**不要问**"要不要生成图片"——按决策树走，选中 ai 时只需在执行前**公告一句**成本，不必等回复（除非命中上面第 1 条）。

> `ImageGen` 的单张成本约 5–10 credits，这是必须主动告知用户的事实，不是可选项。

### 2.3 选定后的一致性纪律

- **一个任务内不混用**。选了 ai 就全程真图；中途某张图生失败，用版式补救或降级占位并**明确标注**，不要悄悄换模式。
- **一个图像节点 = 一次生图 + 一次绑定**，绝不重试。单节点严重失败最多重试 1 次。
- 真图链路固定为：`ImageGen` → `register_assets` → `curl -X PUT` → `upload_images`。
  ⛔ `G()` **只有 `"placeholder"`** 一个合法 type，`ai` / `stock` 都不存在。
- 多尺寸套图走 `references/poster-multisize-pipeline.md`（一张母版 + 图生图派生），不要每尺寸独立生成。
- 生图工具**不可用**时：切 placeholder + 告知用户 + 在交付里给出建议 prompt。⛔ 不许伪造产物、不许贴外部图库 URL。

## 三、`<ardot_design_style>` → 风格模板

宿主注入风格模板时，按模板说明拉取 md 作为视觉基底，并**跳过 Step 4**（`search_style_guide` / `build_style_guide`）。

### 3.1 判定表

| 情况 | 动作 |
|---|---|
| 有注入 + 模板 md 可读 | Read 模板 → 直接作为基底执行；**不调** `search_style_guide` / `build_style_guide` |
| 有注入 + 模板 md 读不到 | **降级走 Step 4**，并在交付说明里记一句（模板失效，已用检索替代） |
| 无注入 + 用户给了明确风格（自由文本 / `DESIGN.md` / tokens） | **跳过 Step 4**，按用户约束执行 |
| 无注入 + 用户没给风格 | 走 Step 4：Read `style-guide.md` → `search_style_guide` → `build_style_guide` |
| 有注入 + 用户给了冲突风格 | **用户优先**；模板只填补用户没指定的维度 |

### 3.2 部分覆盖规则

模板常常只定义了一部分（例如只有配色和字体，没有布局节奏）：

- 模板**已定义**的维度 → 用模板，不许"优化"掉。
- 模板**未定义**的维度 → 用 `style-guide.md` + 类型指南补齐，不要因为模板没写就留空。
- 用户显式约束**覆盖**模板同维度值，其余维度仍用模板。

### 3.3 该问用户的情况

只有一个：用户给了**两条互相矛盾**的风格指令（"要极简" + "要信息密度拉满"），
且无法判断哪条优先 → 问一句以哪条为准。其余情况自行裁决并在交付里说明。

> ⛔ `fetch_style_guide` / `fetch_style_guide_tags` 这两个工具**不存在**。风格关键词灵感读
> `references/style-guide-tags.md`。

## 四、三块的协同（一次任务里的实际顺序）

```
Step 0  探测画布通道 + 确认文件就绪
        ├─ 通道失败 → Spec Mode（references/spec-mode.md），到此为止
        └─ 文件开关：注入 or 等价判定表（§1.1）→ create/open **只发一次**
Step 1  fetch_editor_state + fetch_variables（并行，不可跳过）
Step 2  创意 or 组合分诊
Step 3  类型指南（fetch_guidelines / 本地 guidelines-*.md / logo / 多尺寸产线）
Step 4  风格：注入模板 or 用户约束 or search/build（§3.1）
Step 5–6 空间定位（locate_available_space）+ 检视（batch_read / capture_layout）
Step 7  执行 batch_edit（每批 ≤ 25 ops）
        └─ 图片模式：注入 or 决策树（§2.1）→ 需 ai 时**先报成本**
Step 8  分层校验（T1–T5）→ 交付（海报类追加 export_nodes PNG）
```

**注入与等价的差异只体现在 Step 0 / Step 4 / Step 7 的"要不要问"与"默认走哪条"。流程骨架、Step 编号与 `SKILL.md` 完全一致。**

## 五、常见误判（都是实际踩过的）

| 误判 | 后果 | 正确做法 |
|---|---|---|
| 把"建个 CNB issue"当设计任务建了画布文件 | 多出一个空 .ardot，用户困惑 | 宾语非设计产物 → ambiguous，先问 |
| 为"确认建成功"再调一次 create | 建出两个文件 | 用 `fetch_file_info` 确认 |
| 没注入就每次问"要不要生成图片" | 体验断裂，用户嫌烦 | 按决策树直接判，只报成本 |
| 选了 ai 中途某张失败就偷偷换占位 | 交付物质量不一致且用户不知情 | 明确告知 + 标注哪张是占位 |
| 有模板还去调 `search_style_guide` | 白烧 token，风格还可能被覆盖 | 有模板就跳过 Step 4 |
| 用户给了 `DESIGN.md` 还套模板 | 违背"用户指引优先" | 用户约束覆盖模板 |
