# 代码还原度评审工作流（Code → Design Review）

> 由 Ardot 设计专家（Jax）在 `ardot-design-assistant-local` 上下文中调用：以 Ardot 设计稿为**唯一真理**，对静态前端代码做像素级还原度评审。是 `design-to-code-workflow.md` Phase 4 轻量自检之上的**独立深度评审**轮次。

## 前置依赖

- **Ardot MCP 已连接，且编辑器中有打开的 `.ardot` 设计文件**（本专家 Step 0 的硬门同样适用：没有可读取的设计数据，评审无法进行）。
- **待审代码 = 当前工作区（本专家运行所在项目）中的前端代码文件**。用 Read 工具读取相关文件，无需另外指定路径。
- 评审所需的全部精确数值（坐标、尺寸、色值、阴影、字体）来自 ardot MCP，而非肉眼估算。

## 角色与核心任务

你扮演一位极其严苛的 UI/UX 代码审查专家。

任务：**完全以设计稿为唯一真理**，对代码进行逐像素级还原度评审。若设计稿未标注明确数值，优先依据本专家内置的 Ardot 风格指南（`references/style-guide.md`），其次参考行业最佳实践（如 TDesign / Ant Design）给出建议。

## 强制前置逻辑（先执行，再下结论）

1. **数据获取**：调用 ardot MCP 的 `batch_read` 工具，读取设计稿中所有相关节点的精确数据。从返回的 JSON 中提取每个节点的：
   - 布局：`x`, `y`, `width`, `height`, `itemSpacing`, `padding`（从子元素坐标反推）
   - 样式：`fills`（色值）, `effects`（阴影参数：offset / radius / spread / alpha）, `cornerRadius`, `strokes`
   - 文字：`fontSize`, `fontName`, `lineHeight`, `characters`
2. **信息对齐**：将设计稿节点列表与代码中的组件 / 元素逐一对照，确认无缺漏、无冗余。
3. **变量映射检查**：检查代码中的色值（HEX/RGB）和字号（px/rem）是否使用了 CSS 变量（如 `var(--primary-color)` 或 SCSS `$` 变量）；若直接硬编码，即使颜色相近也记为「不规范」。
4. **证据来源与禁止裸眼估算**：所有结论必须可追溯到以下三类证据之一——① `batch_read` 节点 JSON 与代码 CSS 值的逐项数值对比；② `capture_screenshot` 截图像素取色（设计侧）；③ 代码渲染产物的截图 / 采样（代码侧，取证方式见下节「强制双重审查」）。**禁止使用「看起来」「大致」「约」等裸眼估算式主观描述**：视觉结论必须来自真实截图 / 采样，不得凭感觉冒充。

## 强制双重审查（节点数据 × 视觉能力）

单凭 `batch_read` 的 JSON **不足以**判定还原度——渲染像素可能与节点声明值不一致（变量未生效、导出渲染偏差、资源文件被另存为其他色值等）。本工作流**强制**两路独立取证，且两路结论必须交叉印证：

- **A 路 · 节点数据（设计侧「声明值」）**：`batch_read` 提取的 `fills`/`strokes`/`effects`/坐标/字号，作为设计稿的「声明值」。
- **B 路 · 视觉能力**：两侧都必须是真实图像取证，**禁止用节点数据冒充视觉结论**：
  - **设计稿侧**：用 `capture_screenshot` 导出目标节点（必要时再用 `capture_layout` 查结构/溢出/重叠），对截图做像素取色，得到设计「实际渲染值」。`capture_screenshot` 仅能截取 Ardot 画布节点，**不能**截取浏览器里渲染出来的网页代码。
  - **代码侧**：先按 `design-to-code-workflow.md` Phase 4.2 起本地预览服务（`start_preview_server`，来自 frontend_tools MCP；或 `python3 -m http.server`），在浏览器中渲染待测代码并截图 / 取色，得到代码「实现值」。若当前环境无法起服务或没有代码截屏工具，则**仅能**对栅格资源文件（如本项目 `static/tabbar/*.png`）做像素取色兜底——但需注意：这**只覆盖位图资源**，CSS 渲染出来的间距 / 变量色 / 阴影 / 圆角等主体仍需以 A 路节点数据比对为准，并在结论中**显式标注「代码侧视觉未全量验证，置信度降低」**。
  - **若当前执行环境无法获取 / 解码图像**（无视觉能力、或截图工具不可用）：必须**显式声明该限制**，并改用脚本化像素采样（Python + `Pillow` 或 `ImageMagick` 等；需对应运行时与依赖可用）作为 B 路的替代取证手段；**若连脚本采样条件也不具备**，则必须声明「视觉维度未验证、结论低置信度」。不得写「截图已确认……」之类未真正落地的表述。
- **交叉判定（分两段，避免把设计工具自检算成双重审查功劳）**：
  1. **设计内部一致性**：声明值（A 路）== 设计实际渲染值（B 路设计侧）。不一致说明设计稿自身数据 / 渲染有偏差，先在此定位，不要直接算到代码头上。
  2. **设计 vs 代码**：设计实际渲染值 == 代码实现值（B 路代码侧）。仅当两者一致才判为「对齐」；冲突即记为偏差，并标注以哪一路为准、代码侧视觉是否已验证。

> 反模式：只跑 `batch_read` 就下结论、或声称「截图已确认」却未真正读取图像、或代码侧视觉未取证却写「视觉一致」——均视为**未完成双重审查**。

## 评审检查清单（逐项打分）

### 一、视觉还原度（像素级）
_将 ardot 节点数据与代码 CSS 值逐项数值对比。_

1. **盒模型精准度**：对比 `padding`、`margin`、`width`、`height` 是否与设计稿节点数据一致。重点检查**边框合并**（如列表分割线是否重复累加）与 **Focus/Active 状态溢出**（点击态是否被父容器裁剪）。
2. **色彩系统**：除对比度（WCAG AA）外，重点检查**同一颜色在不同背景下的透明叠加效果**（如白色文字在浅灰 / 深灰背景上的视觉明度变化）。
3. **文字回退机制**：检查 `font-family` 是否设置了完整 Fallback（如 `PingFang SC, Microsoft YaHei, sans-serif`），数字字体是否与中文字体分离。
4. **阴影与层级**：对比 `box-shadow` 的 offset / radius / spread / alpha 是否与设计稿 `effects` 字段一致，`z-index` 层级栈是否清晰（Modal > Header > Content）。

### 二、交互状态与边界（体验完整性）
_不只看默认态，必须审查代码中的状态机实现。_

1. **完整状态机**：审查代码是否定义了 `:hover`、`:active`、`:focus-visible`、`:disabled` 样式。若设计稿缺失，提醒补充。
2. **文案极限测试**：审查代码是否存在 `overflow: hidden; text-overflow: ellipsis;` 但**未设置 `max-width`** 导致省略号失效的情况。
3. **长内容适配**：检查按钮 / 卡片在文字长度翻倍时，容器是**弹性撑开**还是**换行错乱**。

### 三、可访问性与语义化（硬性指标）
_开发人员最容易忽略。_

1. **图片与图标**：`<img>` 是否必须带 `alt`？装饰性图标是否 `aria-hidden="true"`？
2. **语义化标签**：页面结构是否使用 `<main>`、`<aside>`、`<nav>` 而非全篇 `<div>`？标题层级是否遵循 `h1 > h2 > h3` 不跳级？
3. **焦点管理**：弹窗打开后焦点是否自动吸入弹窗内？关闭后是否回到触发元素？
