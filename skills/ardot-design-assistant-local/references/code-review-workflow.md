# 设计↔代码双向校对工作流（Design ↔ Code Review）

> 由 Ardot 设计专家（Jax）在 `ardot-design-assistant-local` 上下文中调用。本工作流包含两种**方向相反、方法同源**的校对模式：
> - **模式 A（代码→设计稿）**：以 Ardot 设计稿为**唯一真理**，审代码是否还原设计（深度还原度评审，见「模式 A」章节）。
> - **模式 B（设计稿→代码）**：以**已实现的真实代码**为真理，逐节点核对设计稿并**改设计稿去贴合代码**（本专家反向校对场景，见「模式 B」章节）。
>
> 两种方法共用同一套取证纪律（见下方「头条硬门：双证据缺一不可」）。是 `design-to-code-workflow.md` Phase 4 轻量自检之上的**独立深度校对**轮次。

## 头条硬门：双证据缺一不可（两种模式通用）

> **禁止仅凭节点数据（A 路）下「已对齐 / 还原 / 一致」结论。** 单凭 `batch_read` 的 JSON **不足以**判定还原度——渲染像素可能与节点声明值不一致（**变量未生效、变量值被误设、导出渲染偏差、资源文件被另存为其他色值、字体回退**等）。本工作流**强制**两路独立取证且交叉印证：
> - **A 路 · 节点数据（声明值）**：`batch_read` 提取的 `fills`/`strokes`/`effects`/坐标/字号，作为「声明值」。
> - **B 路 · 实际渲染值**：对目标节点 `capture_screenshot` 导出 PNG，再用 **脚本化像素采样（Python + Pillow）** 读真实 RGB 像素（中位数抗文字/图标干扰），得到「实际渲染值」。**本专家在当前环境无视觉能力（读图返回「不支持图片」），因此 B 路一律走脚本化像素采样，不得声称「已看图确认」；若连 Pillow/ImageMagick 等运行时也不具备，则必须显式标记「视觉维度未验证、结论低置信度」。**
> - **交叉判定**：声明值（A）== 实际渲染值（B）== 真理源值（设计稿或代码 CSS，视模式而定）。三段任一冲突即记为偏差，并标注以哪一路为准、视觉是否已验证。
>
> 反模式：只跑 `batch_read` 就下结论、或声称「截图已确认」却未真正采样像素、或把节点声明值直接冒充「实际渲染」——均视为**未完成双重审查**，结论无效。
>
> 实证：本硬门已由一次受控实验验证——将 `Card Background` 变量值误设为与页面背景同色（#1a1a1a）后，A 路 `batch_read` 的填充引用「绑定该变量」一字未变（看似正常），但 B 路像素采样抓到实际渲染为 #1a1a1a ≠ 期望 #222222（MISMATCH）。详见 `outputs/ardot-review/pixel_probe/像素探针实验记录.md`。

## 模式选择（先判定走哪条）

| 用户表述（典型） | 走哪条 | 真理源 | 产物 |
|------|------|------|------|
| "代码还原度 / 还原设计稿 / 像素级走查代码" | **模式 A** | 设计稿 | 代码修复清单（P0–P2） |
| "和代码对比一下 / 对齐真实代码 / 校对设计稿 / design to code align / 这个设计稿和实际写的代码一不一样" | **模式 B** | 真实代码 | 设计稿 `batch_edit` 操作清单 + 逐节点对齐判定 |

> 模式 B 是本项目（aura 微信小程序）的高频场景：代码已上线、设计稿是后期补的，需要让设计稿反过来贴合代码。模式 B 的**双证据硬门尤其关键**——设计稿变量绑定「声明正常」但变量值错误时，A 路完全看不出，只有 B 路像素能抓。

## 模式 A：代码 → 设计稿 还原度评审

> 以下「前置依赖 / 角色 / 强制前置逻辑 / 强制双重审查 / 检查清单 / 输出格式」为模式 A 完整规程。模式 B 复用同一套「双证据」纪律，差异仅在真理源与产物，见文末「模式 B」章节。

## 前置依赖

- **Ardot MCP 已连接，且编辑器中有打开的 `.ardot` 设计文件**（本专家 Step 0 的硬门同样适用：没有可读取的设计数据，评审无法进行）。
- **待审代码 = 当前工作区（本专家运行所在项目）中的前端代码文件**。用 Read 工具读取相关文件，无需另外指定路径。
- 评审所需的全部精确数值（坐标、尺寸、色值、阴影、字体）来自 ardot MCP，而非肉眼估算。

## 角色与核心任务

你扮演一位极其严苛的 UI/UX 代码审查专家。

任务：**完全以设计稿为唯一真理**，对代码进行逐像素级还原度评审。若设计稿未标注明确数值，优先依据本专家内置的 Ardot 风格指南（`references/style-guide.md`），其次参考行业最佳实践（如 TDesign / Ant Design）给出建议。

## 强制前置逻辑（先执行，再下结论）

1. **数据获取**：调用 ardot MCP 的 `batch_read` 工具，读取设计稿中所有相关节点的精确数据。从返回的 JSON 中提取每个节点的：
   - 布局：`x`, `y`, `width`, `height`, `itemSpacing`, `padding`（从子元素坐标反推）
   - 样式：`fills`（色值）, `effects`（阴影参数：offset / radius / spread / alpha）, `cornerRadius`, `strokes`
   - 文字：`fontSize`, `fontName`, `lineHeight`, `characters`
2. **信息对齐**：将设计稿节点列表与代码中的组件 / 元素逐一对照，确认无缺漏、无冗余。
3. **变量映射检查**：检查代码中的色值（HEX/RGB）和字号（px/rem）是否使用了 CSS 变量（如 `var(--primary-color)` 或 SCSS `$` 变量）；若直接硬编码，即使颜色相近也记为「不规范」。
4. **证据来源与禁止裸眼估算**：所有结论必须可追溯到以下三类证据之一——① `batch_read` 节点 JSON 与代码 CSS 值的逐项数值对比；② `capture_screenshot` 截图像素取色（设计侧）；③ 代码渲染产物的截图 / 采样（代码侧，取证方式见下节「强制双重审查」）。**禁止使用「看起来」「大致」「约」等裸眼估算式主观描述**：视觉结论必须来自真实截图 / 采样，不得凭感觉冒充。

## 强制双重审查（节点数据 × 视觉能力）

单凭 `batch_read` 的 JSON **不足以**判定还原度——渲染像素可能与节点声明值不一致（变量未生效、导出渲染偏差、资源文件被另存为其他色值等）。本工作流**强制**两路独立取证，且两路结论必须交叉印证：

- **A 路 · 节点数据（设计侧「声明值」）**：`batch_read` 提取的 `fills`/`strokes`/`effects`/坐标/字号，作为设计稿的「声明值」。
- **B 路 · 视觉能力**：两侧都必须是真实图像取证，**禁止用节点数据冒充视觉结论**：
  - **设计稿侧**：用 `capture_screenshot` 导出目标节点（必要时再用 `capture_layout` 查结构/溢出/重叠），对截图做像素取色，得到设计「实际渲染值」。`capture_screenshot` 仅能截取 Ardot 画布节点，**不能**截取浏览器里渲染出来的网页代码。
  - **代码侧**：先按 `design-to-code-workflow.md` Phase 4.2 起本地预览服务（`start_preview_server`，来自 frontend_tools MCP；或 `python3 -m http.server`），在浏览器中渲染待测代码并截图 / 取色，得到代码「实现值」。若当前环境无法起服务或没有代码截屏工具，则**仅能**对栅格资源文件（如本项目 `static/tabbar/*.png`）做像素取色兜底——但需注意：这**只覆盖位图资源**，CSS 渲染出来的间距 / 变量色 / 阴影 / 圆角等主体仍需以 A 路节点数据比对为准，并在结论中**显式标注「代码侧视觉未全量验证，置信度降低」**。
  - **若当前执行环境无法获取 / 解码图像**（无视觉能力、或截图工具不可用）：必须**显式声明该限制**，并改用脚本化像素采样（Python + `Pillow` 或 `ImageMagick` 等；需对应运行时与依赖可用）作为 B 路的替代取证手段；**若连脚本采样条件也不具备**，则必须声明「视觉维度未验证、结论低置信度」。不得写「截图已确认……」之类未真正落地的表述。
- **交叉判定（分两段，避免把设计工具自检算成双重审查功劳）**：
  1. **设计内部一致性**：声明值（A 路）== 设计实际渲染值（B 路设计侧）。不一致说明设计稿自身数据 / 渲染有偏差，先在此定位，不要直接算到代码头上。
  2. **设计 vs 代码**：设计实际渲染值 == 代码实现值（B 路代码侧）。仅当两者一致才判为「对齐」；冲突即记为偏差，并标注以哪一路为准、代码侧视觉是否已验证。

> 反模式：只跑 `batch_read` 就下结论、或声称「截图已确认」却未真正读取图像、或代码侧视觉未取证却写「视觉一致」——均视为**未完成双重审查**。

## 评审检查清单（逐项打分）

### 一、视觉还原度（像素级）
_将 ardot 节点数据与代码 CSS 值逐项数值对比。_

1. **盒模型精准度**：对比 `padding`、`margin`、`width`、`height` 是否与设计稿节点数据一致。重点检查**边框合并**（如列表分割线是否重复累加）与 **Focus/Active 状态溢出**（点击态是否被父容器裁剪）。
2. **色彩系统**：除对比度（WCAG AA）外，重点检查**同一颜色在不同背景下的透明叠加效果**（如白色文字在浅灰 / 深灰背景上的视觉明度变化）。
3. **文字回退机制**：检查 `font-family` 是否设置了完整 Fallback（如 `PingFang SC, Microsoft YaHei, sans-serif`），数字字体是否与中文字体分离。
4. **阴影与层级**：对比 `box-shadow` 的 offset / radius / spread / alpha 是否与设计稿 `effects` 字段一致，`z-index` 层级栈是否清晰（Modal > Header > Content）。

### 二、交互状态与边界（体验完整性）
_不只看默认态，必须审查代码中的状态机实现。_

1. **完整状态机**：审查代码是否定义了 `:hover`、`:active`、`:focus-visible`、`:disabled` 样式。若设计稿缺失，提醒补充。
2. **文案极限测试**：审查代码是否存在 `overflow: hidden; text-overflow: ellipsis;` 但**未设置 `max-width`** 导致省略号失效的情况。
3. **长内容适配**：检查按钮 / 卡片在文字长度翻倍时，容器是**弹性撑开**还是**换行错乱**。

### 三、可访问性与语义化（硬性指标）
_开发人员最容易忽略。_

1. **图片与图标**：`<img>` 是否必须带 `alt`？装饰性图标是否 `aria-hidden="true"`？
2. **语义化标签**：页面结构是否使用 `<main>`、`<aside>`、`<nav>` 而非全篇 `<div>`？标题层级是否遵循 `h1 > h2 > h3` 不跳级？
3. **焦点管理**：弹窗打开后焦点是否自动吸入弹窗内？关闭后是否回到触发元素？

## 模式 B：设计稿 → 代码 反向对齐（以真实代码为真理，改设计稿）

> 触发词见「模式选择」表。本模式不产出代码修复清单，而是产出**设计稿 `batch_edit` 操作清单**，让设计稿逐节点贴合已上线的真实代码。

### B-1. 前置依赖（与模式 A 不同处）

- **真理源 = 当前工作区已实现的真实前端代码**（本专家运行所在项目，如 `pages/wallpaper/wallpaper.wxss`）。用 Read 工具读取相关文件获取精确数值（rpx/px、色值、字号、间距、圆角、字重）。
- **待校对对象 = Ardot 设计稿中对应页面 / 组件的节点**。
- 代码与设计稿的**元素映射**必须先建立（代码里的 `.ip-wrap` ↔ 设计稿 `IPSection-Container` 等），映射错则后续全错。

### B-2. 强制取证（双层，缺一不可）

**第一层 · 设计稿自身一致性（防「声明正常、渲染错了」）** —— 这是模式 B 最容易翻车的地方，必须做：
1. **A 路**：`batch_read`（建议 `resolveVariables:true`）读设计稿节点 `fills`/`boundVariables`/坐标/字号，得到「声明值」。
2. **B 路**：`capture_screenshot` 导出目标节点 PNG → Python+Pillow 读**中位数像素 RGB**，得到「设计实际渲染值」。
3. **交叉**：声明值 == 实际渲染值？不一致即设计稿**自身**有 bug（典型：变量值被误设导致卡片 invisible、字体回退、父级 `clipsContent`/透明度叠加改变可见色），先在**设计侧**定位，不要算到代码头上。

**第二层 · 设计渲染值 == 代码 CSS 值（真理源比对）**：
- 把 B 路得到的「设计实际渲染值」与 Read 出来的「代码 CSS 值」（含 `var(--app-*)` 解析后的实际色）逐项数值比对。
- 仅当两者在容差内（RGB ≤6 / 间距 ≤2rpx≈1pt）一致，才判该节点「已对齐」。
- 冲突即记为偏差，**产物是 `batch_edit` 操作**（改设计稿去贴合代码），并标注以代码为准。

> ⚠️ **禁止**：只跑 `batch_read` 看到 `boundVariables:某变量` 就判「对齐」——变量值可能在文件里被误设，A 路看不到，只有 B 路像素能抓（已实证，见头条硬门注记）。

**B-2.5 平台原生 / 框架托管 UI 的特殊取证——真理源不止配置值**

当真理源是**平台或框架托管渲染的 UI 组件**（非手写 CSS/HTML，而是由配置 + 资源文件驱动渲染，例如各平台的 tabBar、顶部栏、系统控件）时，「真实代码」= **配置值 + 被配置引用的静态资源文件 + 平台实际渲染行为**，三者缺一不可：

1. **配置值**（颜色、尺寸等）仍按 B-2 读取比对。
2. **静态资源文件必须打开核实**：配置只声明"某状态引用哪个资源"，但**该资源本身长什么样（颜色、是否带装饰背景）配置里看不出**——必须 `Read` 打开被引用的真实资源文件，或截真实 App，才能知道该状态真实画面。
3. **渲染行为不可凭记忆/通用知识推断**：选中/高亮等状态常不只是改一处属性（可能同时换资源 + 变色多通道）。这类行为光看配置推断不出，必须看资源文件或实机渲染。

> ⚠️ **反模式**：① 把"我对某平台原生组件渲染行为的理解"当真理源，未核实资源文件/未跑真机就断言其表现；② B 路用**设计稿自己的截图**充当"真实 App 渲染"——设计稿是待评审对象，不能拿它当真理，Layer-2 的"代码实现值"必须来自真实资源像素或实机截图。

### B-3. 输出格式（强制结构化）

#### 1. 逐节点对齐判定表
| 节点 ID | 元素 | 代码期望（CSS 解析值） | A 路声明值 | B 路像素值 | 结论（对齐 / 偏差 + 原因） |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 53:158 | IP 输入框 | #222 / 44pt / 6pt | ... | ... | 对齐 / 偏差：… |

#### 2. 设计稿修改清单（batch_edit ops，按 P0–P2 分级）
- **P0（阻断性）**：设计稿与代码严重不符、或设计稿自身渲染已错（变量值误设 / 不可见）。
  - `[节点 53:xxx]`：当前 X，代码期望 Y。**→ 修复**：`U("53:xxx", { ... })`。
- **P1（体验性）**：间距 / 圆角 / 字重 / 字号偏差，视觉可感知。
  - ...
- **P2（规范性）**：硬编码色值未绑定 token、文本节点宽度未 hug、占位色未用 `--app-text-placeholder` 等。
  - ...

#### 3. 置信度声明（必填）
- 明确写出：哪些节点**已 B 路像素验证**（高置信）；哪些**仅 A 路、未采样像素**（低置信，需用户在微信开发者工具肉眼复核）。
- 若环境无 Pillow/ImageMagick，整体标「视觉维度未验证、结论低置信度」。

### B-4. 已验证的方法论资产（可复用）

- 像素采样脚本：`outputs/ardot-review/pixel_probe/sample.py`（中位数像素 + 期望色比对，取最新时间戳截图，容差 RGB≤6）。
- 受控实验记录：`outputs/ardot-review/pixel_probe/像素探针实验记录.md`（三阶段：基线 / 注入变量值失败 / 还原，证明 B 路价值）。
- 执行 B 路时直接复用上述脚本，截图落到 `pixel_probe/` 目录即可。
